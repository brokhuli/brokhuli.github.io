## Professional Disclaimer

This is
a product I owned professionally as the Lead Software Architect for Alstom Transporation's simulation team. I don't personally
own the product or the codebase, so this case study will be high-level and not include code references.

## Problem

Within my scope of ownership, I inherited a CBTC train simulation product with roots dating back to 1995.
The product was used by integration and V&V teams to test wayside signaling software. It was also delivered
to the customer to simulate trains as part of an operator training system. The product was a critical component of the overall system,
and its accuracy and reliability were essential for the success of the projects it supported.
The train simulator, created virtual trains, added them to the orchestrated system,
and simulated real-time kinematics for movement, and real-time functional interaction
with wayside systems. The product's architecture was a monolithic C#/WPF codebase.
The product had to manually and regularly change to support new features of signalling projects.
Repeated adaptations over the years deteriorated the integrity of the codebase. Changes to support
new projects, often introduced bugs and regressions. This was amplified by non-extensible nature of the codebase in addition to
the lack of appropriate CI/CD and unit testing to ensure backwards compatibility.

### Main Issues

- Product updates, even simple ones, were high-risk to break functionality and backwards compatibility.
- Due to the poor, tightly coupled architecture, years of changes led to significant technical debt.
- Inaccurate simulation led to field escapes in wayside signalling software.
- A dedicated 5 person team was required to maintain the product, which was a significant cost for the company.

## Complexity

### Business Goals

- Reduce the maintenance cost of the train simulator by reducing the required team size supporting it from 5 to 3.
- Reduce field escapes in wayside signalling software by improving the accuracy and reliability of the train simulator.
- Containerization to enabled cloud deployment and reduce the need for dedicated hardware for the simulation.
- Improve the speed of updates and new feature development by implementing a more modular and extensible architecture
- Enhance the user experience for integration and V&V teams by providing a more responsive and interactive simulation environment.

### Technical Challenge

The technical challenge was to redesign and refactor the train simulator's architecture to improve its maintainability, extensibility, and reliability. This involved:

- Decoupling the tightly coupled components of the monolithic codebase.
- Implementing a modular architecture that allowed for easier updates and maintenance.
- Ensuring the accuracy of the simulation to prevent field escapes in wayside signalling software.
- Creating a deterministic simulation system that also allowed for user interaction and negative testing in real-time.
- Introducing CI/CD pipelines and unit testing to ensure backwards compatibility and reduce the risk of regressions.
- Introducing observability and monitoring to quickly identify and address issues in the simulation.

## Architectural Design

### High-Level Approach

As this is a professional project, I won't be able to share detailed architecture diagrams or code snippets.
However, I can describe the high-level architectural approach taken to address the challenges.

The product was developed as a greenfield product, designed from the ground up. A discovery phase was conducted to understand and map the existing system requirements to the product. Since, this product simulates real world rolling stock and vehicle software, the actual vehicle software was reverse engineered as well to understand logic that existed "in between" the requirements.

#### Backend Architecture

The backend architecture was designed as a modular monolith using a hybrid of Domain-Driven Design and Hexagonal Architecture principles. The following structure is a rough outline of the backend architecture:

/src
-/DataModel
--/Models
--/Interfaces
--/Controllers
-/SimulationModel
--/PhysicsModels
-/SimulationLogic
--/Initialization
--/Movement
--/PlatformStopping
--/Emergency
--/etc
-/Api
--/GraphQL
--/ProprietaryApi

The data model was designed to be pure and independent of the simulation logic. It contained simply data and properties with no business logic. This allowed for easy testing and reusability of data model components.
The simulation logic and state management were handled entirely in the backend. A simulation engine drove the timing for the logic sequences essentually managing logic that needs to execute either in sequence or concurrently. As well as managing different timings allowing for smaller intervals and more CPU for deterministic tight loops, and alleviating timing for non-critical logic.
The backend/frontend seperation also allowed for headless running of the simulation, which was essential for containerized deployment and automated testing by V&V team.

#### Frontend Architecture

The frontend was responsible for visualization and user interaction. User discovery sessions were made to understand the needs of the integration and V&V teams, and the frontend was designed to provide a more responsive and interactive simulation environment. The key was to give users a high level of visibility into the state of the simulation. Prior versions were based on forms with labels and values. The blazor frontend has simple 2d visualizations of trains moving on tracks, giving the user instant visual context into the state of the simulation.
GraphQL was used for the API between the backend and the frontend. The backend was not responsible for pushing updates to the frontend. This alleviated this taks from the backend and puts the responsibility on the frontend to query the correct data. The backend simply allows for a fairly complete querying and command system so that backend alterations are not required to support different frontends or other software like telemetry or test frameworks.

#### Observability

The simulation was designed with observability in mind, allowing for real-time monitoring and analysis of the system's behavior. This included logging, metrics collection, and alerting mechanisms to ensure that any issues could be quickly identified and addressed. Snapshots of structured logs and screenshots of the frontend are generated during a system fault or by user request. These offer a details view of the state of the system during a malfunction. This snapshot is packaged and given to developers to troubleshoot the isse. This greatly improved mean time to resolution for issues found in the field, and also allowed for quicker troubleshooting of issues found during development and testing.

#### CI/CD and Testing

CI/CD pipelines were implemented to automate the build, testing, and deployment processes. Unit testing was introduced to ensure backwards compatibility and reduce the risk of regressions. The modular architecture allowed for easier testing of individual components, and the deterministic nature of the simulation made it easier to identify and fix issues.
Playwright was used to create automated end-to-end tests for the simulation, which was essential to quickly identify any issues with the simulation and ensure that it was functioning correctly.

### Key Design Decisions

- Greenfield product development rather than piecemeal modernization. Due to the tightly coupled, monolithic structure, heavy technical debt, and inability to extend the product, rewrite was the way to go.
- Modular Monolith architecture allowed for easier development and troubleshooting by a small team while still achieving the desired modularity and extensibility.
- Data Model Purity: The data model was designed to be pure and independent of the simulation logic, allowing for easy testing a reusability of data model components.
- DDD/Hexagonal Architecture Hybrid: The architecture was influenced by Domain-Driven Design and Hexagonal Architecture principles, which helped to create a clear separation of concerns, allow for unit testing, and create ubiquitous domain language.
- Deterministic Simulation: The simulation was designed to be deterministic, ensuring that the same inputs would always produce the same outputs, which was crucial for testing and debugging.
- Backend-Frontend Separation: The simulation logic and state management were handled entirely in the backend, while the frontend was responsible for visualization and user interaction. This separation allowed for a more responsive and interactive simulation environment while keeping the core logic centralized and easier to maintain.
- Backend handled all state and logic, frontend just for visualization and user interaction. This separation of concerns allowed for a more responsive and interactive simulation environment while keeping the core logic centralized and easier to maintain.

## Architectural Tradeoffs

- Greenfield vs Modernization - Due to the tightly coupled, monolithic structure, heavy technical debt, and inability to extend the product, rewrite was the way to go.
- Modular Monolith vs Microservices - Easier to troubleshoot issues found in field. Generally did not have services that needed to scale or be used by other systems.
- DDD/Hexagonal vs Clean Architecture (or others) - DDD/Hexagonal allowed for appropriate clean boundaries and separation of concerns which allowed for testing, extensibility, and maintainability, while also using ubiquitous language for non-technical stakeholders
- C# vs C++ - Primarily used to leverage existing team's background in .Net. Note that this decision was made prior to advent of heavy AI-assisted development. If I were to design the same product today, i would use C++ and React as the barrier to enter other programming languagues has reduced. C++ offers better ability to control the determinism of the physics loops which would allow for a more reliable and consistent system.
- Blazor vs WPF/Qt - A web frontend was essential for containerized deployment of the system moving away from dedicated hardware or virtual machines with operating system license costs.
- Blazor vs React/Angular/Vue - Blazor was simply chosen to leverage existing team's background in .Net. Blazor Server was used over WebAssembly as it is the backend's responsibility to run logic, manage state and data. Also, Blazor Server reduces mitigations for cybersecurity compliance.
